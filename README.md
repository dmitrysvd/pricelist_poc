# Стенд: две модели хранения версионированного прайс-листа (X и Y)

Замеры моделей X и Y на одних данных и одних запросах. Стенд даёт цифры и не даёт рекомендации.
Сводка: `results/REPORT.md`; нейтральные выводы и что модели поддерживают с трудом: `docs/findings.md`; методика и допущения: `docs/assumptions.md`.

## Запуск

```bash
./run_all.sh                       # docker-Postgres, датасеты t1/t5/t20, сверка, все сценарии, отчёт
DATASETS="x10" ./run_all.sh        # объём x10 (850 тыс. услуг, 5 типов)
SKIP_GEN=1 SCENARIOS=1,2 ./run_all.sh   # только замеры на готовых датасетах
```

Нужны docker и uv; Postgres 18 поднимается в контейнере `pricelist-pg`, сокет в `./.pgsock`.

## Устройство

| что | где |
|---|---|
| общие таблицы (филиал, услуги, категории, типы цен) | `common/models.py` |
| схема X / Y (Django-модели + миграции) | `model_x/models.py`, `model_y/models.py` |
| интерфейс операций (один метод = одна операция продукта) | `bench/iface.py` |
| SQL моделей | `model_x/impl.py` (+ вариант (б) и X·lat в `impl_b.py`), `model_y/impl.py` |
| генератор: одна лента изменений -> X и Y | `common/management/commands/gen.py` |
| сценарии и параметры прогонов | `bench/scenarios.py` |
| раннер: время, EXPLAIN, WAL, строки, Δ размер | `bench/runner.py` |
| сверка X == Y (чтение / после записи) | `manage.py verify`, `manage.py verify_writes` |
| отчёт | `manage.py report` -> `results/REPORT.md`, планы в `results/explain/` |

Методы интерфейса не выполняют SQL сами, а возвращают шаги транзакции (`Op`). Выполняет и замеряет их общий раннер, поэтому метрики снимаются одинаково для обеих моделей.
